# How open-source MTG engines model game state (architecture / data-model level)

Scope: code-verified from cloned repos `magefree/mage` (XMage) and `Card-Forge/forge` (Forge), plus the design blog for `wingedsheep/argentum-engine` (Argentum). Cockatrice is skipped (no rules engine). Citations are repo file paths or URLs. I mark each claim **[verified]** (read in code/docs) or **[inferred]**.

> CR note: rule-number checks below use the current Comprehensive Rules. Relevant anchors: "dies" = CR 700.4 (put into a graveyard from the battlefield); object changes zones → new object = CR 400.7; layer system = CR 613; layer-7 sublayers = CR 613.4; dependency = CR 613.8; last-known-information = CR 608.2h; "look back in time" for dies/leaves-the-battlefield triggers = CR 603.10 / 608.2i; tokens cease to exist off the battlefield = CR 111.7 / 110.5g (state-based action, CR 704).

## 1. XMage (magefree/mage) — Java

### Permanent vs Card vs game object; identity
- **[verified]** Class hierarchy: `MageObject` → `MageObjectImpl` → `CardImpl` → `PermanentImpl` (abstract) → `PermanentCard` / `PermanentToken` / `PermanentMeld`. So a Permanent literally *is-a* Card by inheritance. (`Mage/src/main/java/mage/game/permanent/PermanentImpl.java:51` `public abstract class PermanentImpl extends CardImpl implements Permanent`; `PermanentCard.java:24`.)
- **[verified]** A `PermanentCard` does **not** hold the original card; it holds a **blueprint copy** in a `card` field, and the class comment flags this as fragile: `// blueprint e.g. a copy of the original card ... TODO: wtf, it modified on getCard/getBasicMageObject/getMainCard() ... must be fixed!` (`PermanentCard.java:26-29`).
- **[verified]** Identity = a `UUID objectId` (from `MageObject`) plus a **zone-change counter (ZCC)**. The pair `(sourceId, zoneChangeCounter)` is wrapped in `MageObjectReference` — "*A object reference that takes zone changes into account*" (`Mage/src/main/java/mage/MageObjectReference.java:16-26`). This is how XMage answers "is this the same object it was a moment ago?" — used for attachments, attacking/blocking sets, mutate, pairing, etc. (`PermanentImpl.java:96-117` uses `MageObjectReference` for `attacking`, `blockingSet`, `pairedPermanent`). This is the implementation of CR 400.7's "new object" semantics (a moved object has no memory of its prior existence).
- **[verified]** A new battlefield arrival is a **new `PermanentCard`** built from the card; the constructor passes `card.getId()` as the permanent's id, with explicit author uncertainty about that choice: `// TODO: wtf, must research - is it possible to have diff ids for same card id?!` (`PermanentCard.java:36-41`). The permanent's ZCC is frozen at creation and intentionally does not change while on the battlefield (`PermanentCard.java:287-304`, again littered with `// TODO: wtf ... is it buggy here?!`).

### Continuous effects / layer system — computed, via reset+reapply
- **[verified]** Power/toughness/types/colors/abilities are **recomputed**, not persisted. The driver is `GameState.applyEffects()` which each pass calls `battlefield.reset(game)` (resetting every permanent to its base card values) and then `effects.apply(game)` (`Mage/src/main/java/mage/game/GameState.java:668-678`). An up-counting `applyEffectsCounter` tracks recompute generations (`GameState.java:117`).
- **[verified]** `PermanentCard.reset()` re-copies all characteristics from the blueprint card (or `secondSideCard` if transformed), re-applies mutate, and resets P/T to base (`PermanentCard.java:116-128`, `copyFromCard()` at `:142-216`).
- **[verified]** The CR-613 layer system (CR has exactly **7 layers**: copy, control, text, type, color, ability, P/T) is applied imperatively in fixed order in `ContinuousEffects.applyEffects()`: CopyEffects_1 (incl. FaceDown 1b — matches CR 613.2a/613.2b), ControlChanging_2, TextChanging_3, TypeChanging_4, ColorChanging_5, AbilityAdding_6, then P/T split into CharacteristicDefining_7a, SetPT_7b, ModifyPT_7c, Counters_7d, SwitchPT_7e, plus extra non-CR `PlayerEffects` and `RulesEffects` layers (`Mage/src/main/java/mage/abilities/effects/ContinuousEffects.java:973-1155`).
  - **CR-fidelity note:** XMage's *separate* `Counters` sublayer reflects the **pre-April-2021** CR. The current CR (613.4) has only **four** layer-7 sublayers — 7a (characteristic-defining), 7b (set P/T), 7c (modify P/T, with counters folded in), 7d (switch) — because the 2021 update merged the old counters sublayer into the modify sublayer. XMage's 5-way split is thus an out-of-date-but-equivalent encoding; Forge's single MODIFYPT(7c) (below) matches the current CR. `PlayerEffects`/`RulesEffects` are engine constructs, not CR layers.
- **[verified]** Timestamp ordering is tracked per-layer via `lastEffectsListOnLayer` keyed by a "timestampGroupName" (`ContinuousEffects.java:57, 189, 240`). Dependency handling (CR 613.8) exists within layer 6 / `applyLayer()` (`:1044-1106, 1165-1199`).

### Zone changes — new objects; "dies" as a typed zone transition
- **[verified]** Moving onto the battlefield constructs a fresh permanent object: `permanent = new PermanentCard(card, ...)` / `new PermanentCard(card.getMainCard(), ...)` in `ZonesHandler` (`Mage/src/main/java/mage/game/ZonesHandler.java:416, 423`); ZCC is bumped on the move (`:484-486`). So zone changes create new game objects (new identity), matching CR 400.7's "new object" rule. (Per CR, the token exception applies: a token leaving the battlefield does not persist as a new object — it ceases to exist as a state-based action, CR 111.7/110.5g/704.)
- **[verified]** "Dies" is modeled as a **specialized zone-change trigger from BATTLEFIELD to GRAVEYARD**, matching CR 700.4 ("dies" = "is put into a graveyard from the battlefield"; note this is purely zone-based and applies to tokens as well as cards): `DiesSourceTriggeredAbility` calls `super(Zone.BATTLEFIELD, Zone.GRAVEYARD, ...)` with text "When {this} dies" (`Mage/src/main/java/mage/abilities/common/DiesSourceTriggeredAbility.java:23`). General "leaves the battlefield" is a `ZoneChangeEvent` with `fromZone == BATTLEFIELD` and any destination. There is a whole family: `DiesCreatureTriggeredAbility`, `DiesOneOrMoreTriggeredAbility`, `DiesAttachedTriggeredAbility`, etc.
- **[verified]** Last-known-information (CR 608.2h; the dies/leaves-the-battlefield "look back in time" rule is CR 603.10/608.2i) is handled by `game.getPermanentOrLKIBattlefield(...)` so effects resolve against an LKI snapshot after the object left.

### Tokens, copies, merged (Mutate), multi-face cards
- **[verified]** Tokens are `PermanentToken` (sibling of `PermanentCard`); a `Token`/`TokenImpl` blueprint produces them.
- **[verified]** Mutate / merged permanents are stored *on the permanent* as ID lists, not a separate object: `mutations` (UUIDs merged into this permanent), `mutationsForView` (ordered mutate stack incl. self), `mutatedAbilities`, and `topMutation` (`PermanentImpl.java:116-119`); `reset()` calls `applyMutate(game)`.
- **[verified]** Meld is its own subclass `PermanentMeld extends PermanentCard` (`Mage/src/main/java/mage/game/permanent/PermanentMeld.java:11`).
- **[verified]** Multi-face cards are a rich subclass tree under `mage/cards/`: `SplitCard`(+`SplitCardHalf`), `ModalDoubleFacedCard`(+`...Half`), `TransformingDoubleFacedCard`(+`...Half`), `AdventureCard`/`OmenCard`/`PrepareCard` (card + spell-option halves), `RoomCard`, `MeldCard`, `LevelerCard`, plus an abstract `CardWithHalves`/`CardWithSpellOption` (`ls mage/cards/`). A permanent created from a DFC stores both faces: `card` (front) and `secondSideCard` (back), with a `transformed` boolean selecting which one `reset()` copies from (`PermanentCard.java:71-85, 119-123`). DFCs/split cards are explicitly forbidden as direct `PermanentCard` inputs — you must pass the correct half (`PermanentCard.java:51-68`, throws `IllegalArgumentException`).

### Behavior: code, not data
- **[verified]** XMage represents card behavior as **compiled Java**: every card is its own class assembled from reusable `Ability`/`Effect` objects (the `mage/abilities/effects/...` tree). Abilities are attached to the permanent and re-registered on each `copyFromCard` so continuous/triggered abilities track the new object id (`PermanentCard.java:152-163`).

### Author commentary / rationale
- **[verified]** The most candid design commentary lives **in the code as `// TODO: wtf ...` comments** acknowledging the blueprint-card and ZCC scheme are bug-prone (`PermanentCard.java:26-29, 287-304`; `MageObjectReference(Ability)` constructor is `@Deprecated // cause of many bugs, see issue #10479` at `MageObjectReference.java:60-66`).
- **[verified]** Architecture overview (modules: game logic, cards/sets, server, client, comms; heavy Singleton use; design-pattern catalog) comes from the Delft DESOSA 2018 chapter — but that URL now returns HTTP 401, so only the search-engine summary is available, not the primary text. (https://delftswa.gitbooks.io/desosa2018/content/xmage/chapter.html — currently inaccessible.)
- **[verified]** Developer commentary that MTG's effect space resists any "sane structured format" and that XMage's JSON output is hard to parse appears on the HN thread (https://news.ycombinator.com/item?id=38651346).

## 2. Forge (Card-Forge/forge) — Java

### Permanent vs Card vs game object; identity
- **[verified]** Forge has **no separate Permanent class**. There is one `Card extends GameEntity` (`forge-game/src/main/java/forge/game/card/Card.java:87`). "Permanent-ness" is just being a `Card` whose zone is the battlefield.
- **[verified]** A `Card` holds **multiple named states**: `Map<CardStateName,CardState> states` plus a `currentState` / `currentStateName` (default `Original`) (`Card.java:91-94`). `CardState` (`forge-game/src/main/java/forge/game/card/CardState.java`, ~1116 lines) holds the actual base characteristics (name, types, P/T, colors, abilities) for one face/mode.
- **[verified]** Object *kind* is an enum field `GamePieceType gamePieceType` with values `CARD, TOKEN, EFFECT, COPIED_SPELL, ATTRACTION, CONTRAPTION, PLANAR, SCHEME, AVATAR, DUNGEON` (`forge-core/src/main/java/forge/card/GamePieceType.java`; field at `Card.java:94`, helpers `isToken()/isCopiedSpell()/isEffect()` at `:1045-1065`). So "card vs token vs copy" is data on one class, not subclasses.
- **[verified]** Identity = `int id` on `GameEntity` (`forge-game/src/main/java/forge/game/GameEntity.java:50-66`, with a telling `dangerouslySetId(int)`). For the rules' "new object" semantics (CR 400.7) Forge also carries a **game timestamp** (`getGameTimestamp()/setGameTimestamp()`), separate from the layer timestamps.

### Zone changes — also create a NEW object (+ LKI copy)
- **[verified]** This corrected my initial assumption. Although a `Zone` holds a `CardCollection` of `Card` (`forge-game/src/main/java/forge/game/zone/Zone.java:46-94`), `GameAction.changeZone()` does **`copied = new CardCopyService(c).copyCard(false)`** and adds the *copy* to the destination zone, while building a last-known-information copy of the original via `CardCopyService.getLKICopy(c)` (`forge-game/src/main/java/forge/game/GameAction.java:155-207, 508`) — Forge's implementation of CR 400.7 (new object) plus CR 608.2h (LKI). The new object inherits the old game timestamp only in specific cases (`copied.setGameTimestamp(c.getGameTimestamp())` at `:209`), and is reset to `Original` state on leaving the battlefield (`:247-251`).
- **[verified]** Exceptions where the **same** object is reused (no fresh copy): copied-spells and immutable effects (`return c` at `:100-107`), dev-mode entries (`:110-116`), illegal moves (tokens that left, instants/sorceries to battlefield — `:124-133`), and same-zone "suppress" moves (`:153`). The "token that left" branch reflects CR 111.7/110.5g (a token off the battlefield ceases to exist and can't move further). Zone.add even takes a `latestState` LKI argument (`Zone.java:94`).
- **[verified]** "Dies" vs "leaves battlefield": per CR 700.4, "dies" = the battlefield→graveyard path specifically (applies to tokens and cards alike). Destruction routes through `destroy()` → fires `GameEventCardDestroyed`, runs `TriggerType.Destroyed`, sets `updateWasDestroyed(true)`, then `moveToGraveyard()` (`GameAction.java:2135-2180`, `:1572`, `:2115-2167`). A generic move from battlefield to any zone is `changeZone`/`moveTo...`. Note destruction (CR 701.7) is only one *cause* of dying; `wasDestroyed` is a flag distinguishing destruction from other deaths (e.g. lethal-damage SBA, zero toughness, sacrifice).

### Continuous effects / layer system — computed via per-layer recompute + dependency graph
- **[verified]** Layers are the enum `StaticAbilityLayer`: `COPY(1), CONTROL(2), TEXT(3), TYPE(4), COLOR(5), ABILITIES(6), CHARACTERISTIC(7a), SETPT(7b), MODIFYPT(7c), RULES(8)`, with `CONTINUOUS_LAYERS` and a `CONTINUOUS_LAYERS_WITH_DEPENDENCY` subset (`forge-game/src/main/java/forge/game/staticability/StaticAbilityLayer.java`). Forge's single `MODIFYPT(7c)` (no separate counters sublayer) matches the **current** CR 613.4, where counters are folded into the modify sublayer. `RULES(8)` is a Forge construct, not a CR layer (CR has 7 layers).
- **[verified]** The master recompute is `GameAction.checkStaticAbilities()`: it clears prior static effects, collects all continuous static abilities across the game, sorts by timestamp (`effectOrder`), then iterates `for (layer : CONTINUOUS_LAYERS)` applying each (`GameAction.java:1070-1120, 1088`).
- **[verified]** **Real CR-613.8 dependency handling** uses a JGraphT directed graph: `DefaultDirectedGraph<StaticAbility,DefaultEdge> dependencyGraph`, edges added when applying one ability changes the affected-set of another, only for `CONTINUOUS_LAYERS_WITH_DEPENDENCY` (`GameAction.java:1279-1357`).
- **[verified]** P/T and types are **computed in getters from base + timestamp-keyed change maps**, not stored. `getCurrentPower()` starts from `getBasePower()` then folds `getPTIterable()` (set-P/T effects override) (`Card.java:4459-4467`); counters add separately via `getPowerBonusFromCounters()` (`:4480-4487`) — consistent with current CR 613.4c, where set is 7b and modify (abilities and counters together) is 7c. Types come from `getChangedCardTypes()` which concatenates `changedCardTypesByText` (layer 3), `changedCardTypesCharacterDefining` (layer 4), `changedCardTypes` (layer 4) (`Card.java:4078-4090`). Copy effects are a `NavigableMap<Long,CardCloneStates> clonedStates // Layer 1`, timestamp-keyed (`Card.java:164`).
- **[inferred]** Net difference vs XMage: both recompute, but Forge keeps the layered changes **attached to the live `Card`** as timestamp-keyed maps and folds them in accessors; XMage wipes the permanent to base each `applyEffects` pass and re-imperatively writes the modified fields. Forge's approach makes "what effects currently apply" introspectable per-card; XMage's makes the post-layer snapshot the source of truth.

### Tokens, copies, merged (Mutate), multi-face
- **[verified]** Tokens: `gamePieceType == TOKEN` plus `tokenCard` boolean (`Card.java:204, 1045-1057`); a real token reaching the stack as a copied permanent keeps a `copiedPermanent` reference (`GameAction.java:221-225`).
- **[verified]** Copy effects: `CardCloneStates` objects in the `clonedStates` layer-1 NavigableMap (`Card.java:164`, file `forge-game/src/main/java/forge/game/card/CardCloneStates.java`).
- **[verified]** Merge/Mutate: a `CardCollection mergedCards` and a back-pointer `Card mergedTo` live on the Card; helpers `getTopMergedCard()` (index 0), `addMergedCard()`, `hasMergedCard()`; many accessors special-case `hasMergedCard() ? getMergedCards() : new CardCollection(this)` so the merged stack is treated as one permanent whose top card is canonical (`Card.java:107-116, 1425-1442, 676-931`). There is a `ZoneType.Merged` (`GameAction.java:118`).
- **[verified]** Multi-face: handled via `CardStateName` (Original, LeftSplit, RightSplit, Flipped, Backside, Meld, FaceDown, EmptyRoom, PreparedSpell, Specialize...) selected by `setState()/changeToState()` (`Card.java:483-630`). Split/DFC therefore are one `Card` with several `CardState`s rather than separate card objects — opposite of XMage's per-half subclasses. Forge has `setBackSide`, room unlock tracking (`unlockedRooms`, `unlockAbilities` at `:225-226`), specialize/prepared states (`GameAction.java:247-263`).

### Behavior: data-driven scripts
- **[verified]** Forge cards are **text scripts** ("forge script" / `.txt` card files) parsed by `CardFactory`/`CardFactoryUtil` into `SpellAbility`/`StaticAbility` objects (`forge-game/.../card/CardFactory.java`, referenced via the mirror at github.com/riking/mtg-forge). This is the major architectural contrast with XMage's per-card Java classes. Static continuous abilities feed directly into the layer engine described above.

### Author commentary / rationale
- **[verified]** Project framing ("dynamic, open-source Rules Engine ... built in Java ... encourages contributing cards") from the project site (https://card-forge.github.io/forge/) and README (https://github.com/Card-Forge/forge). The data-driven card-scripting choice is what enables non-programmer card contributions.
- **[verified]** Numerous in-repo `TODO`s document edge-case anxiety, e.g. the mutate+attraction death comment (`GameAction.java:144`) and the copied-spell→token comment (`:223-224`).
- **[verified]** Open issues confirm model stress points: token copies of MDFC inheriting both faces (magefree #8476, mirrored discussion) and MDFC transform handling (Card-Forge #8594).

## 3. Argentum (wingedsheep/argentum-engine) — Kotlin, pure ECS

Source: author's design blog (https://wingedsheep.com/building-argentum-a-magic-the-gathering-rules-engine/). This is the explicit "design doc / rationale" target. All **[verified]** from that doc; I did not read its code.

- **Permanent vs card vs object:** Everything is an **entity = a unique id**; cards, players, stack spells, even a continuous effect like "Giant Growth gave +3/+3" are entities. Data lives in **components (pure data bags, no behavior)**; all logic is in **systems**. No class hierarchy for permanents — identity fluidity is handled by components, because "you can't re-parent an object at runtime."
- **State model:** Immutable, deterministic transition `(GameState, GameAction) → ExecutionResult(GameState, List<GameEvent>)` — no I/O, enabling replay/undo/netcode by replaying inputs.
- **Continuous effects / layers:** Separates **base state (stored)** from **projected state (computed)**. The 7 layers (CR 613) are applied in order (copy, control, text, type, color, abilities, P/T). Per the current CR (613.4) layer 7 has **four** sublayers — 7a characteristic-defining, 7b set, 7c modify (counters included), 7d switch (the blog's "P/T sublayers" framing predates the 2021 counters/modify merge; older descriptions list five). P/T is computed, never stored mutated. Expiry just **removes the effect entity** — no reversal needed because base state was never mutated. Edge cases like Humility-on-itself use **trial application**: apply tentatively, detect dependencies, then apply for real (the same conceptual approach as Forge's dependency graph and CR 613.8).
- **Zone changes:** hidden-info filtering is server-side per zone (library hidden, hand owner-only, battlefield/graveyard/stack public); the client only captures intent and never validates legality. (The doc does not explicitly state whether a zone change mints a new entity id, but the ECS "new object" framing implies it — **[inferred]**; note per CR 400.7 nontoken objects become new objects while tokens cease to exist, CR 111.7.)
- **Tokens/copies/MDFC:** subsumed by the entity+component model — a token or copy is just an entity with the appropriate components/projection; no dedicated classes (**[inferred]** from the "everything is an entity, identity is fluid via projections" description; the blog doesn't enumerate MDFC/mutate specifics).
- **Behavior:** **pure data DSL**. "Traditional engines hardcode card logic ... Argentum treats cards as pure data" — card definitions compose effect primitives, new cards need no core changes. This is the most data-driven of the three (Forge is data-via-scripts; XMage is code).
- **Rationale stated by author:** ECS chosen specifically because OO inheritance can't model a creature that changes types/controllers/abilities at runtime ("can't re-parent an object at runtime"); immutability chosen for trivial replay/undo/network determinism.

## Cross-engine comparison (the load-bearing distinctions)

| Concern | XMage | Forge | Argentum |
|---|---|---|---|
| Permanent representation | subclass: `PermanentImpl extends CardImpl` (`PermanentCard`/`Token`/`Meld`) | same `Card` class, on battlefield zone; kind via `GamePieceType` enum | entity + components |
| Identity | `UUID` + zone-change-counter (`MageObjectReference`) | `int id` + game timestamp | entity id |
| Zone change → new object? (CR 400.7) | **Yes** — `new PermanentCard` (`ZonesHandler.java:416`) | **Yes** — `new CardCopyService(c).copyCard()` + LKI copy (`GameAction.java:207`), with documented exceptions | yes (inferred) |
| Layer 7 sublayers vs current CR (613.4: 7a/7b/7c/7d) | 5-way split incl. separate Counters_7d (reflects pre-2021 CR) | single MODIFYPT(7c), counters folded in (matches current CR) | "P/T sublayers" (4 current; blog framing predates 2021 merge) |
| Layers engine | recompute: reset all + imperative apply (`GameState.applyEffects`) | recompute per-layer over timestamp-sorted statics + JGraphT dependency graph (`GameAction.checkStaticAbilities`) | base vs projected, trial application |
| P/T & types | computed each pass, written onto reset permanent | computed in getters from base + per-layer timestamp maps | computed projection |
| "Dies" (CR 700.4) vs "leaves" | typed trigger BATTLEFIELD→GRAVEYARD (`DiesSourceTriggeredAbility`) | `destroy()`→`GameEventCardDestroyed`+`wasDestroyed` flag (destruction is one cause of dying), then `moveToGraveyard` | (not detailed) |
| Mutate/merge | ID lists on permanent (`mutations`, `topMutation`) | `mergedCards` collection + `mergedTo` + `ZoneType.Merged` | components (inferred) |
| Multi-face (split/MDFC) | per-half subclasses (`SplitCardHalf`, `...CardHalf`) + `secondSideCard` | one Card, multiple `CardState` selected by `CardStateName` | data (inferred) |
| Behavior | compiled Java per card | data-driven text scripts | pure-data DSL |

Common ground worth noting: **all three keep base/printed state separate from current state and recompute the layered result** rather than mutating base in place; **all three handle a permanent leaving the battlefield as becoming a new object (CR 400.7) and rely on last-known-information snapshots (CR 608.2h)** (XMage `getPermanentOrLKIBattlefield`, Forge `getLKICopy`). (Caveat: tokens are the CR exception — they cease to exist off the battlefield, CR 111.7/110.5g, rather than persisting as new objects.)
